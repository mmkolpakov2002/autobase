# Домашнее Задание №2: Построение системы с учетом наблюдаемости (Observability)

В этом документе описано решение по настройке мониторинга для HA-кластера PostgreSQL и API-сервиса, развернутых в ДЗ №1. Решение выполнено в концепции **Infrastructure as Code (IaC)** с использованием Ansible.

## 1. Архитектура решения

Учитывая сетевые ограничения и требования к метрикам, система мониторинга построена следующим образом:

### 1.1. Внутренний контур (Сбор метрик)
Развернут на узле-балансировщике (`balancer`).
*   **Prometheus (v3.8.0):** Центральный сервер сбора метрик. Конфигурация (`prometheus.yml`) генерируется динамически на основе инвентаря Ansible, что позволяет автоматически обнаруживать новые ноды.
*   **Alertmanager (v0.29.0):** Управление алертами. Получает уведомления от Prometheus при срабатывании правил.
*   **Blackbox Exporter (v0.27.0):** Выполняет синтетические проверки доступности API приложения.

### 1.2. Внешний контур (Визуализация)
Для визуализации используется **Курсовая Grafana**.
*   **Datasource 1 (Infrastructure):** Подключен мой Prometheus (`Prometheus-Student-7`), который собирает метрики с ВМ, БД и компонентов кластера.
*   **Datasource 2 (K8s):** Подключен общекластерный Prometheus (VictoriaMetrics) для получения метрик Ingress-контроллера, недоступных изнутри виртуальной сети.

### 1.3. Агенты сбора метрик (Exporters)
*   **Node Exporter (v1.10.2):** Установлен на всех узлах кластера для сбора системных метрик (CPU, Memory, Disk, Network).
*   **Postgres Exporter (v0.18.1):** Установлен на узлах СУБД. Использует выделенного пользователя `postgres_exporter` с ролью `pg_monitor`.
*   **Patroni & Etcd:** Сбор метрик осуществляется через нативные API этих сервисов (порты 8008 и 2379) по протоколу HTTPS.

---

## 2. Детали реализации (Ansible)

*   В `inventory.yml` выделена группа `monitoring_server` для размещения Prometheus и Alertmanager.
*   В `group_vars/all.yml` зафиксированы версии компонентов.
*   Написаны собственные роли для каждого компонента мониторинга.
*   Реализован паттерн "Download Locally": бинарные файлы скачиваются на управляющую машину (localhost) и копируются на целевые серверы, что решает проблему отсутствия прямого доступа в интернет с ВМ.

---

## 3. Алертинг

В Prometheus загружены правила (`alert.rules.yml`) для отслеживания критических состояний системы:
1.  **HighRequestLatency:** Предупреждение при высокой задержке ответов API (>0.5s).
2.  **HighErrorRate:** Критический алерт при недоступности API (проверка через Blackbox).
3.  **HostHighCpuLoad:** Предупреждение при утилизации CPU > 80%.
4.  **PostgresDown:** Критический алерт при недоступности экземпляра PostgreSQL.

## 4. Визуализация (Сдача ДЗ)

Все дашборды настроены в **Курсовой Grafana** (папка "Student-7").

### 4.1. Метрики инфраструктуры
Используют Datasource: `Prometheus-Student-7`.
*   **PostgreSQL Database:** Детальные метрики производительности БД (TPS, блокировки, буферы).
*   **Node Exporter Full:** Системные ресурсы всех узлов кластера.
*   **Etcd v3:** Состояние кворума и производительность кластера Etcd.
*   **Patroni:** Статус репликации и состояния кластера Patroni.

### 4.2. Метрики API (Golden Signals)
Дашборд: **"Student-7 API Monitoring"**.
Реализованы **4 золотых сигнала** на базе метрик **Ingress Nginx** (Datasource: VictoriaMetrics):
1.  **Traffic:** RPS (запросов в секунду) к API.
2.  **Latency:** 99-й перцентиль времени ответа.
3.  **Errors:** Количество 5xx ошибок.
4.  **Saturation:** Распределение кодов ответа HTTP.

## 5. Обслуживание

### Диагностика
Скрипт `./check_hw2.sh` проверяет доступность портов и статус таргетов Prometheus.

### Удаление (Cleanup)
Для удаления компонентов мониторинга без влияния на работу БД используется плейбук:
```bash
ansible-playbook -i inventory.yml playbooks/remove_monitoring.yml
```
