# Домашнее Задание №3: Нагрузочное тестирование и поиск узких мест

В рамках задания было проведено исследование производительности развернутого сервиса API и кластера PostgreSQL. Тестирование проводилось в два этапа (внутреннее и внешнее), чтобы разделить ограничения приложения и сетевого периметра.

## 1. Методика тестирования

### 1.1. Инструментарий и Архитектура
*   **Инструмент:** [k6](https://k6.io/).
*   **Скрипты:** `stress_test.js` (внутренний), `stress_test_external.js` (внешний).
*   **Маршрутизация:** Все запросы отправляются с заголовком `Host: student-7.local` для обработки Ingress-контроллером.

### 1.2. Профиль нагрузки (Workload Profile)
Сценарий эмулирует смешанную работу пользователей с API:
*   **80% Read (GET /Cities):** Нагружают CPU приложения и чтение из реплик БД.
*   **20% Write (POST /Cities):** Создают нагрузку на Master-ноду БД (WAL, репликация) и диск.

**Схема подачи нагрузки (Ramp-up):**
1.  **Разгон:** 0 → 50 VUs (1 мин).
2.  **Плато:** 50 VUs (3 мин).
3.  **Стресс:** 50 → 200 VUs (2 мин) — поиск точки деградации.
4.  **Остывание:** 200 → 0 VUs (30 сек).

### 1.3. Критерии качества (SLO) и определение ошибок
Система считается работающей штатно при соблюдении указанных условий:
1.  **Latency (p95):** < 200мс (внутр.) / < 500мс (внешн.).
2.  **Error Rate:** < 1%.

**Что считается ошибкой:**
В метрике `http_req_failed` учитываются прикладные и транспортные ошибки:
*   HTTP-статусы, отличные от `200` (для GET) или `200/201` (для POST).
*   Разрывы соединений (`EOF`), таймауты (`request timeout`), отказ в соединении (`connection refused`).

## 2. Результаты тестирования

### Прогон №1: Внутреннее тестирование (Internal)
**Точка запуска:** Виртуальная машина `balancer` (внутри контура).
**Цель:** Оценить чистую производительность приложения и БД без влияния интернета и внешних фаерволов.

**Результаты:**
*   **Пиковая нагрузка:** 200 VUs.
*   **Success Rate:** **100%** (Ошибок нет).
*   **Latency (p95):** ~5.06s (Деградация).
*   **RPS:** ~38.5 req/s.

**Лог выполнения:**
```text
  █ THRESHOLDS
    http_req_duration
    ✗ 'p(95)<200' p(95)=5.06s

    http_req_failed
    ✓ 'rate<0.01' rate=0.00%
```

При росте нагрузки до 200 пользователей система продолжила обрабатывать запросы без сбоев (HTTP 5xx отсутствуют, БД доступна), но время отклика сильно выросло (в 25 раз выше SLO).
Это указывает на проблемы на уровне пода приложения (.NET API). Приложение ставит запросы в очередь, так как не успевает их процессить. Лимит подключений к БД (`max_connections=100`) достигнут не был.

### Прогон №2: Внешнее тестирование (External)
**Точка запуска:** Локальная машина (WSL), через Интернет.
**Цель:** Оценить работу системы с точки зрения реального пользователя.
**Адрес цели:** Внешний IP `77.105.182.79`.

**Результаты:**
*   **Пиковая нагрузка:** 200 VUs.
*   **Success Rate:** **~29.7%** (более 70% запросов упали).
*   **Latency (p95):** ~8.66s.
*   **Типы ошибок:** `unexpected EOF`, `request timeout`.

**Лог выполнения:**
```text
  █ THRESHOLDS
    http_req_duration
    ✗ 'p(95)<500' p(95)=8.66s

    http_req_failed
    ✗ 'rate<0.01' rate=70.31%
```

**Анализ:**
При попытке подать нагрузку из внешней сети, подавляющее большинство запросов завершилось сетевыми ошибками, не дойдя до приложения. Это, возможно, поведение механизмов защиты периметра облака (Anti-DDoS / Rate Limiting), которые разрывают соединения при превышении лимитов с одного IP-адреса.
Т.е. это уровень не приложения, а сети.

## 3. Выводы

1.  **Узкое место приложения (Bottleneck):**
    Приложение ограничивается ресурсами в Kubernetes. Для масштабирования необходимо, например, увеличить `resources.limits.cpu` в манифесте пода или настроить Horizontal Pod Autoscaler (HPA). База данных PostgreSQL в текущей конфигурации справляется с нагрузкой и не является узким местом.

2.  **Узкое место инфраструктуры:**
    Внешний доступ ограничен параметрами по сетевой защите облачного провайдера. Реальная пропускная способность для внешних клиентов с одного IP-адреса значительно ниже, чем может обработать кластер внутри.

3.  **Максимальная производительность:**
 *   **Внутренняя:** Система стабильна до ~50 VUs с приемлемым Latency.
 *   **Внешняя:** Стабильная работа возможна только при низкой конкурентности (до 20 VUs) из-за ограничений сети.
