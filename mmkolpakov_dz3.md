# Домашнее Задание №3: Нагрузочное тестирование и поиск узких мест

В рамках задания было проведено исследование производительности развернутого сервиса API и кластера PostgreSQL. Тестирование проводилось в несколько этапов для изоляции ограничений приложения, сети и бизнес-логики.

## 1. Методика тестирования

### 1.1. Инструментарий и Архитектура
*   **Инструмент:** [k6](https://k6.io/).
*   **Скрипты:** Базовый (`stress_test.js`/`stress_test_external.js`) и Продвинутый сценарный (`stress_test_universal.js`).
*   **Маршрутизация:** Запросы отправляются с заголовком `Host: student-7.local` для обработки Ingress-контроллером.

### 1.2. Профиль нагрузки (Workload Profile)
Сценарий эмулирует смешанную работу пользователей ("User Journey"):
1.  **Write (POST /Cities):** 20% трафика. Эмуляция создания ресурса.
2.  **Read (GET /Cities):** 80% трафика. Проверка (Read your own writes) в случае успешного создания.
3.  **Think Time:** Случайная задержка между действиями для реалистичности.

**Схема подачи нагрузки (Ramp-up):**
1.  **Разгон:** 0 → 50 VUs (1 мин).
2.  **Плато:** 50 VUs (3 мин).
3.  **Стресс:** 50 → 200 VUs (2 мин) — поиск точки деградации.
4.  **Остывание:** 200 → 0 VUs (30 сек).

### 1.3. Критерии качества (SLO)
Система считается работающей штатно при соблюдении условий:
1.  **Latency (p95):** < 200мс (внутр.) / < 500мс (внешн.).
2.  **Global Error Rate:** < 1% (технические ошибки: 5xx, timeouts).
3.  **Business SLA (Write):** Операция записи должна занимать < 1 сек.

## 2. Результаты тестирования

### Прогон №1: Внутреннее тестирование (Internal Baseline)
**Точка запуска:** Виртуальная машина `balancer` (внутри контура).
**Цель:** Оценить чистую производительность приложения и БД (CPU/Memory/DB Locks) без влияния внешней сети.

*   **Пиковая нагрузка:** 200 VUs.
*   **Success Rate:** **100%** (Технических ошибок нет).
*   **Latency (p95):** ~5.06s (Сильная деградация).
*   **RPS:** ~38.5 req/s.

**Анализ:** При 200 VUs приложение (.NET API) упирается в лимиты CPU, образуя очередь запросов. PostgreSQL справляется штатно.

---

### Прогон №2: Внешнее тестирование (Network Limits)
**Точка запуска:** Локальная машина (WSL), через Интернет.
**Цель:** Оценить влияние сетевого периметра и Anti-DDoS защиты.

*   **Пиковая нагрузка:** 200 VUs.
*   **Success Rate:** **~29.7%** (Более 70% запросов отбиты сетью).
*   **Типы ошибок:** `unexpected EOF`, `request timeout`.

**Анализ:** Внешний шлюз облачного провайдера разрывает соединения при высокой конкурентности с одного IP.

---

### Прогон №3: Продвинутый тест
**Точка запуска:** Локальная машина (Интернет).
**Особенности:** Использовались кастомные метрики для разделения "технических падений" и "нарушений бизнес-таймаутов".

**Лог выполнения:**
```text
  █ THRESHOLDS
    failed_write_requests
    ✗ 'rate<0.05' rate=66.87%   <-- нарушение бизнес-SLA

    http_req_duration
    ✗ 'p(95)<500' p(95)=11.46s  <-- p95 вырос в 2 раза по сравнению с внутренним тестом

    http_req_failed
    ✗ 'rate<0.01' rate=4.73%    <-- Сетевые ошибки (EOF)
```

**Анализ данных:**
1.  **Soft Outage:** Технически сервер ответил с ошибкой (5xx/Network Error) только в **4.73%** случаев. Однако, **66.87%** операций записи были признаны провальными, так как выполнялись дольше 1 секунды.
2.  **Write Latency:** 99% запросов на запись выполнялись дольше **14.32 сек**.
3.  **Сетевой оверхед:** Внешняя сеть добавила около **6 секунд** задержки (11.46s снаружи против 5.06s внутри).

## 3. Выводы

1.  **Узкое место приложения (Application Bottleneck):**
    Основным ограничителем производительности является **CPU пода приложения** в Kubernetes. При нагрузке выше 50 RPS приложение не успевает обрабатывать очередь, что приводит к росту Latency до 5+ секунд.

2.  **Узкое место инфраструктуры (Network Bottleneck):**
    При доступе извне узким местом становится **сетевой периметр**.
 *   При 200 активных пользователях внешний канал добавляет ~6 секунд задержки.
 *   При агрессивной нагрузке срабатывает защита провайдера (сброс соединений EOF).

3.  **Статус системы:**
 *   **Рабочая зона:** До 50 RPS (стабильная работа).
 *   **Зона деградации:** 50-150 RPS (рост задержек, нарушение SLA по времени ответа, "Soft Outage").
 *   **Зона отказа:** >200 RPS извне (потеря связности).

**Рекомендации:**
*   Масштабировать API (Horizontal Pod Autoscaler).
*   Рассмотреть CDN или балансировщик с более широким каналом для внешних клиентов.
