# Домашнее Задание №1: Развертывание HA-кластера PostgreSQL с Autobase

Этот документ описывает полный процесс развертывания кластера PostgreSQL с использованием проекта Autobase, документирует все шаги, предпринятые для настройки, отладки и решения проблем, возникших в процессе выполнения задания.

**Цель работы:** Развернуть отказоустойчивый кластер PostgreSQL в конфигурации Patroni + etcd + HAProxy на предоставленных виртуальных машинах и подготовить его для дальнейшей интеграции с API-сервисом.

## Раздел 1: Подготовка Управляющего Узла

Перед началом развертывания была произведена подготовка управляющей машины для обеспечения чистоты и предсказуемости окружения.

Работа ведётся на Windows Subsystem For Linux с установленной Ubuntu 22.04.5 LTS.

### 1.1. Клонирование репозитория

Репозиторий проекта `autobase` был склонирован в локальную директорию:
```bash
git clone https://github.com/vitabaks/autobase.git dz1
cd dz1/
```

### 1.2. Создание и активация виртуального окружения Python

Для изоляции зависимостей и использования актуальной версии Ansible было создано виртуальное окружение:
```bash
# Создание окружения
python3 -m venv ~/ansible-env

# Активация (выполняется в каждой новой сессии терминала)
source ~/ansible-env/bin/activate
```

### 1.3. Установка Ansible и зависимостей проекта

Внутри активированного окружения были установлены Ansible и все необходимые библиотеки:
```bash
# Установка Ansible
pip install "ansible>=2.17"

# Установка всех остальных зависимостей из requirements.txt
# (после комментирования строки с фиксированной версией ansible)
pip install -r autobase/automation/requirements.txt
```

### 1.4. Настройка Ansible для локальной разработки

Чтобы Ansible использовал локальные, измененные версии ролей и коллекций, а не глобально установленные, была выполнена следующая настройка в директории `autobase/automation`:

1.  **Создана структура коллекций** с символической ссылкой на загруженный проект. Это заставляет Ansible воспринимать локальную директорию как установленную коллекцию `vitabaks.autobase`.
    ```bash
    # Выполняется в директории automation/
    mkdir -p ./ansible_collections/vitabaks
    ln -s "$(pwd)" ./ansible_collections/vitabaks/autobase
    ```

2.  **Скорректирован `ansible.cfg`**, чтобы указать Ansible пути для поиска локальных коллекций и ролей.
    ```ini
    # automation/ansible.cfg
    [defaults]
    # ...
    collections_paths = ./ansible_collections
    roles_path = ./roles
    ```

## Раздел 2: Конфигурация Развертывания

Для соответствия требованиям домашнего задания были созданы файлы инвентаря и переменных.

### 2.1. Файл инвентаря (`inventory.yml`)

Этот файл описывает топологию кластера, распределяя предоставленные ВМ по логическим группам.

```yaml
---
all:
  vars:
    ansible_user: mmkolpakov
    ansible_ssh_private_key_file: /home/mmkolpakov/.ssh/mipt-wsl22
    ansible_host: 77.105.182.79

  children:
    balancers:
      hosts:
        balancer:
          ansible_port: 27022
    postgres_cluster:
      hosts:
        bd1:
          ansible_port: 27023
        bd2:
          ansible_port: 27024
    etcd_cluster:
      hosts:
        etcd1:
          ansible_port: 27025
        etcd2:
          ansible_port: 27026
        etcd3:
          ansible_port: 27027
    master:
      hosts:
        bd1:
    replica:
      hosts:
        bd2:
```

### 2.2. Файл переменных (`group_vars/all.yml`)

В этом файле собраны все ключевые параметры, переопределяющие стандартное поведение Autobase для развертывания в конкретном случае домашней работы.

```yaml
---
dcs_type: "etcd"
with_haproxy_load_balancing: true
pgbouncer_install: false

patroni_superuser_password: "mmkolpakovPostgresPassword123!"
patroni_replication_password: "mmkolpakovReplicationPassword456!"

# TLS для всех компонентов
tls_cert_generate: true
etcd_tls_enable: true
patroni_etcd_protocol: "https"
patroni_restapi_protocol: "https"

# Отключение требования клиентских сертификатов для etcd,
# так как кластер etcd выделенный. Это упрощает конфигурацию Patroni.
etcd_client_cert_auth: false
patroni_etcd_use_client_cert: false

# Отключение встроенного файрвола для упрощения развертывания в учебной среде
firewall_enabled_at_boot: false

# Базовые правила в pg_hba.conf, включая trust для локальных подключений
host_type: "hostssl"
postgresql_pg_hba:
  - { type: "local", database: "all", user: "all", address: "", method: "trust" }
  - { type: "local", database: "all", user: "{{ patroni_superuser_username }}", address: "", method: "trust" }
  - { type: "host", database: "all", user: "all", address: "127.0.0.1/32", method: "{{ postgresql_password_encryption_algorithm }}" }
  - { type: "host", database: "all", user: "all", address: "::1/128", method: "{{ postgresql_password_encryption_algorithm }}" }
  - { type: "{{ host_type }}", database: "all", user: "all", address: "0.0.0.0/0", method: "{{ postgresql_password_encryption_algorithm }}" }
```

## Раздел 3: Внесенные Изменения в Проект

В ходе адаптации под требования домашнего задания, исходный код проекта `autobase` был проанализирован и доработан. Целью изменений было не только выполнить поставленную задачу, но и повысить надежность, идемпотентность и удобство отладки процесса развертывания.

Все изменения были внесены таким образом, чтобы не нарушать основную логику проекта, а расширять ее и исправлять потенциальные проблемы, выявленные в ходе интеграции и попыток развёртываний.

### 3.1. Архитектурные и Конфигурационные Улучшения

Эти изменения направлены на улучшение структуры проекта и его адаптивности.

1.  **Локализация Коллекции Ansible:**
 *   **Проблема:** При стандартном запуске Ansible использует глобально установленные роли и коллекции, что делает отладку и внесение локальных изменений непредсказуемыми.
 *   **Решение:** В файле `ansible.cfg` были прописаны пути к локальным директориям `roles_path` и `collections_paths`. С помощью символической ссылки проект `autobase` был представлен как локально установленная коллекция `vitabaks.autobase`. Это гарантирует, что Ansible всегда использует код из текущей рабочей директории, позволяя обращаться к ролям через полное имя (FQCN), например `vitabaks.autobase.patroni`.

2.  **Динамическая Генерация `/etc/hosts`:**
 *   **Проблема:** В распределенных системах необходимо, чтобы узлы могли обращаться друг к другу по именам. Ручное ведение файла `/etc/hosts` на каждом узле — трудоемкий и подверженный ошибкам процесс.
 *   **Решение:** Роль `etc_hosts` была доработана. Добавлена переменная `etc_hosts_auto_generate`, которая при значении `true` автоматически собирает IP-адреса и имена всех хостов из инвентаря Ansible и прописывает их в `/etc/hosts` на каждом узле кластера. Это делает инвентарь единственным источником правды о топологии сети.

### 3.2. Повышение Надежности и Идемпотентности

Эти изменения делают процесс развертывания более стабильным и предсказуемым при повторных запусках.

1.  **Очистка DCS (etcd) перед развертыванием:**
 *   **Проблема:** При повторном запуске плейбука после неудачной попытки, старые данные о кластере в `etcd` могли помешать Patroni корректно инициализировать новый кластер.
 *   **Решение:** В плейбук `deploy_pgcluster.yml` добавлен шаг, который очищает пространство имен кластера в `etcd` перед началом развертывания. Это поведение управляется новой переменной `deploy_clean_dcs_on_bootstrap` и включено по умолчанию, что обеспечивает идемпотентность.

2.  **Управление блокировками `apt`:**
 *   **Проблема:** В процессе отладки прерванные запуски Ansible могли оставлять блокировки пакетного менеджера `apt`, что приводило к ошибкам при следующем запуске.
 *   **Решение:** Добавлен шаг, который принудительно завершает процессы `apt` и удаляет файлы блокировок.

3.  **Явное создание пользователей и директорий:**
 *   **Проблема:** Некоторые шаги полагались на то, что пакетный менеджер создаст системного пользователя (`postgres`) или директорию логов. Это могло приводить к ошибкам race condition.
 *   **Решение:** В плейбуки были добавлены явные шаги по созданию пользователя `postgres` и необходимых директорий (`/var/log/patroni` и др.) *до* установки и настройки соответствующих сервисов.

### 3.3. Исправления в Логике TLS и Безопасности

Ключевые исправления, направленные на корректную работу шифрования в заданной конфигурации.

1.  **Гибкое управление аутентификацией по клиентским сертификатам в `etcd`:**
 *   **Проблема:** В оригинальном проекте логика включения/выключения `etcd_client_cert_auth` была жестко привязана к тому, находятся ли `etcd` и `patroni` на одних и тех же узлах. Это не позволяло гибко настроить сценарий с выделенным кластером `etcd`, где требование клиентских сертификатов избыточно.
 *   **Решение:** Введена новая переменная `etcd_force_client_cert_auth`. Если она установлена, ее значение имеет приоритет. В противном случае используется улучшенная автоматическая логика. Это позволило настроить безопасное TLS-соединение **без** требования клиентского сертификата от Patroni, что подходит для топологии из ДЗ.

2.  **Исправление шаблонов `confd` и `patroni`:**
 *   **Проблема:** Шаблоны `confd.toml.j2` и `patroni.yml.j2` не учитывали возможность отключения аутентификации по клиентским сертификатам, что приводило к ошибкам подключения.
 *   **Решение:** В шаблоны добавлены условия `{% if etcd_client_cert_auth %}`, которые включают параметры клиентских сертификатов только тогда, когда это действительно необходимо.

3.  **Динамическая генерация `pg_hba.conf`:**
 *   **Проблема:** Оригинальный `pg_hba.conf` содержал статические правила.
 *   **Решение:** Логика генерации `pg_hba.conf` была вынесена в роль `patroni` и дополнена возможностью автоматической генерации правил (`hostssl ...`) для всех узлов из инвентаря, что делает конфигурацию динамической и менее подверженной ошибкам.

## Раздел 4: Вспомогательные Инструменты

Для упрощения разработки и отладки были созданы дополнительные плейбуки.

### 4.1. Скрипт полной очистки (`cleanup.yml`)

Этот плейбук полностью удаляет все компоненты Autobase с целевых серверов: останавливает и отключает сервисы, удаляет пакеты, конфигурационные файлы, данные, логи, а также системных пользователей. Это позволяет гарантированно начинать развертывание с чистого листа.

**Запуск:** `ansible-playbook -i inventory.yml cleanup.yml`

### 4.2. Скрипт комплексной диагностики (`diagnose.yml`)

Этот плейбук является инструментом для отладки. Он подключается ко всем узлам кластера и собирает всю информацию:
*   Общие системные параметры (uptime, диски, память, firewall, SELinux).
*   Статусы и последние 100 строк логов сервисов `patroni` и `etcd`.
*   Состояние сетевых портов и запущенных процессов.
*   Конфигурационные файлы.
*   Результаты команд `etcdctl` для проверки здоровья кластера `etcd`.
*   Тесты сетевой связности от `patroni` к `etcd` с помощью `curl`.
*   Сравнительный анализ отпечатков CA-сертификатов.

Весь отчет выводится в консоль и сохраняется в лог-файл для дальнейшего анализа.

## Раздел 5: Запуск

После всех подготовительных работ и исправлений, полный цикл развертывания выполняется одной командой (в активированном виртуальном окружении):

```bash
cd ~/dz1/autobase/automation/
ansible-playbook -i inventory.yml playbooks/deploy_pgcluster.yml
```
